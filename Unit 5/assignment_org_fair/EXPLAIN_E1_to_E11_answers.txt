E1 — lib/main.dart
OrgFairApp is a StatelessWidget because it does not hold mutable UI state. It only builds the MaterialApp, sets the theme, and passes the repository into the home screen. Once it is built, it does not change on its own.

OrgListScreen is a StatefulWidget because it owns data that changes while the app is running, such as the search text, favorite IDs, hidden IDs, and registrations. These values are stored in the State object and can change through setState(), so the screen needs to rebuild itself.

The two questions from the slides are:
1. Does the widget need to remember information that changes over time?
2. Does it need to call setState() to update the UI?
For OrgFairApp, the answer is no. For OrgListScreen, the answer is yes.

E2 — lib/screens/org_list_screen.dart
_searchController is disposed in dispose() because it is a long-lived object tied to the TextField. If it is not disposed, it keeps listening to the widget and retains memory even after the screen is removed.

Over time, forgetting to dispose it can cause memory leaks, stale text/input references, and unexpected behavior when the screen is rebuilt or replaced. The controller should be cleaned up when the State is destroyed.

E3 — lib/screens/org_list_screen.dart
The FutureBuilder can go through these states:
1. Loading: snapshot.connectionState is not done yet. The app shows a spinner and the loading message.
2. Error: snapshot.hasError is true. The app shows the error message and a Try again button.
3. Empty: snapshot has data, but the list is empty. The app shows the inbox message.
4. Success: snapshot has data and the list is not empty. The app shows the organization list.

When the fake server mode is "error" and the user presses Try again, the sequence is usually:
- Loading
- Error
- Loading again
- Error again (if the server still fails)
- Then eventually loading -> empty or success if the server changes state.

E4 — lib/screens/org_list_screen.dart
There is no loop watching the text box. Instead, the TextField uses onChanged. Every time the user types, onChanged runs and executes setState(() => _query = value). That rebuilds the widget tree.

Then build() runs again, creates a new q value, and recalculates visible using the search query. In other words, the list updates because user input triggers a rebuild, not because a background watcher is constantly polling the field.

E5 — lib/screens/org_list_screen.dart
If you remove the Expanded widget, Flutter throws a layout error. The usual message is something like:
"Vertical viewport was given an unbounded height"
or
"RenderFlex children have non-zero flex but incoming height constraints are unbounded."

This happens because a Column has children that need a definite height, and a ListView/GridView inside it wants to take the remaining space. The rule is: "constraints go down, sizes go up." The parent gives constraints to the child, and the child decides its own size. Expanded tells the Column: “give this child the remaining space.” Without it, the scrollable child does not know how much vertical space it is allowed to use, so Flutter reports a layout problem.

E6 — lib/widgets/org_card.dart
The star state is not stored inside OrgCard because OrgCard is a StatelessWidget. The value comes from the parent, OrgListScreen, which stores favorites in the set _favoriteIds.

The card receives these values as parameters:
- isFavorite
- isMember
- onTap
- onLongPress

When the user long-presses the card, the parent handler _toggleFavorite(org) runs and calls setState(). This updates _favoriteIds and then rebuilds the parent. The rebuilt parent passes the new isFavorite value into OrgCard, so the star icon changes.

E7 — lib/screens/org_list_screen.dart
Navigator.push() returns a Future. In this code the push is typed as Future<Registration?>:
final registration = await Navigator.of(context).push<Registration>(...);

That future completes with the value passed into Navigator.pop(value) when the pushed route closes. In this app, the value is sent back from the form screen by this line:
Navigator.of(context).pop(registration);
inside JoinFormScreen._submit().

If the user cancels or the screen closes without a value, the future completes with null.

E8 — lib/widgets/org_banner.dart
This widget handles three cases in build():

1. No URL:
   if (url == null) return _placeholder(context, Icons.groups);
   The user sees a placeholder box with a group icon.

2. Image is still downloading:
   loadingBuilder: (context, child, progress) => progress == null ? child : const Center(child: CircularProgressIndicator());
   The user sees a circular progress indicator while the image is loading.

3. Image failed to load:
   errorBuilder: (context, error, stack) => _placeholder(context, Icons.broken_image);
   The user sees a placeholder box with a broken-image icon.

E9 — lib/screens/org_detail_screen.dart
The code checks context.mounted after an await because the widget may be disposed or no longer active while waiting for navigation to finish. The async gap can happen after the screen has been popped, moved, or replaced.

If the widget is no longer mounted, using the old BuildContext is unsafe. The check prevents invalid calls such as Navigator.of(context).pop(...) after the context is no longer valid.

In this case, the await is waiting for the form screen to return a registration. If registration is not null and the context is still mounted, it safely pops the detail screen with the registration value.

E10 — lib/screens/join_form_screen.dart
A GlobalKey<FormState> is a unique identifier for a specific Form widget. It lets the parent State access the corresponding FormState object even though the form is nested inside a widget tree.

It allows the code to call these three important methods on the form:
1. validate() - runs all validators and returns true if the form is valid.
2. save() - calls onSaved for every field so their values are stored in the State.
3. reset() - clears the form values and restores the fields to their initial state.

In the code, these are used in _submit() and _reset().

E11 — lib/screens/join_form_screen.dart
AutovalidateMode.onUserInteraction means validation runs only after the user has interacted with the field. This is friendlier because the form does not show errors immediately before the user has typed anything.

If we used AutovalidateMode.always, validation would run on every rebuild, even when the field is empty. That would show error messages immediately, which is noisy and frustrating for users.

So onUserInteraction is better for a form because it validates when the user is actually using it, but still avoids constant immediate errors before input begins.
